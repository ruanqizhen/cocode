# AI 成本控制

> “一丝一毫，关乎节用。” ——《朱子家训》

从“偶尔用网页版聊两句”转向“用 Claude Code 全天候开发”，很多人的第一课不是技术课，而是账单课：一个复杂的重构会话跑下来，费用可能超出心理预期十倍。

## 复利噩梦

一个普通编码 Agent 在一次复杂重构中，可能要进行上百次 API 调用。最烧钱的不是它最后生成的那几百行代码，而是每次调用都要重复发送的输入 Token。

这就是上下文的复利效应：大模型是无记忆的，每次你跟它说话，它都要把之前的历史记录和引用的几万行代码重新打包再发一遍。对话到第 50 轮时，上下文可能已经膨胀到 200K Tokens。这时你哪怕只说一句“测试通过了，继续”，它也会把前 50 轮的全部历史再发一次。雪球越滚越大，账单就是这样被悄无声息推高的。

记住一个比例：AI 编程账单的 80% 到 90% 都烧在输入 Token 上，也就是“让 AI 阅读理解”的成本上。管住了输入，就管住了账单。方法得当，完全可以在不降低代码质量的前提下，把总成本砍掉 70% 到 85%。

大模型的聪明是要付费的，公式其实很简单：

$$\text{总费用} = (\text{输入 Token} \times \text{单价}) + (\text{输出 Token} \times \text{单价}) - (\text{缓存命中 Token} \times \text{缓存折扣})$$

- 输入 Token（最烧钱的黑洞）：你发送给 AI 的提问、历史对话记录，以及引用的代码文件。在开发中，它往往占据了总体消耗的 80% ~ 90%。
- 输出 Token：AI 回复的代码。计算生成的代价高昂，其单价通常是输入的 3~5 倍。
- 缓存命中 Token（你的利润池）：如果前后两次请求发送的内容高度重合，服务端会直接复用上次的计算结果，这就是提示词缓存（Prompt Caching）。命中缓存的部分能享受大幅折扣。各家的折扣规则经常变，具体以官网为准，但原理不变：让 AI 重复看同样的东西，是防守成本的核心。


## 好钢用在刀刃上

团队里最大的浪费叫“无脑开满配”：不管是加注释、格式化 JSON，还是重命名变量，都直接丢给最贵最强的顶级模型。

真相是，日常编码中 60% 到 80% 都是体力活，这些任务用便宜小模型和用顶级模型，结果几乎一模一样。为体力活付顶级模型的钱，纯属交智商税。

正确姿势是建立分级协作战术：

| 任务层级 | 该派谁上场 | 相对成本 | 为什么这样分 |
| --- | --- | --- | --- |
| 体力活：补全、加注释、格式化 | 本地模型或极速便宜模型 | 最低，本地接近零成本 | 任务简单，小模型足够对付，错了也容易发现 |
| 日常主力：常规功能开发 | 性价比最高的甜点模型 | 较低 | 覆盖 80% 的日常需求，质量和价格的平衡点 |
| 攻坚：复杂重构、疑难 Bug | 推理能力最强的顶级模型 | 最高，只在必要时按需调用 | 难题才配得上最强大脑，用一次就要解决一次 |

模型命名和定价变化极快，本书不列具体数字，请以各厂商官网为准，上表只看相对关系。

在多智能体架构里，这个策略更彻底：让贵的顶级模型只负责高屋建瓴地制定重构计划（Planner），把计划拆成小步骤后，交给便宜模型去执行具体的文件修改（Executor）。用最贵的脑子做决策，用最便宜的手去干活，这就是工程上最划算的分工。

## 上下文主动剪枝

“上下文是钱，上下文是钱，上下文是钱！” 最典型的破产行为，就是无脑 `@Codebase`，把整个项目连带 `node_modules` 一股脑扔给 AI。一个 200K Token 的项目，每问一次就要为这 20 万 Token 全额买单，问十次就买十次，复利噩梦就是这么来的。为了解决这个问题，我们可以采用如下一些战术：

- 战术 1：靶向投喂，拒绝全局扫盲。如果你已经知道问题在哪，就只给相关部分。比如只读 Git Diff 和涉及的函数签名，精确输入 `@src/api/user.js`，而不是让模型把全库读一遍。为什么？因为 AI 的阅读量直接等于你的账单，喂得越准，浪费越少。
- 战术 2：使用 Repo Map 替代全文。Aider 和 Cursor 都支持生成 `repo_map`，它用几千个 Token 就能概括整个代码库的目录结构和核心类、函数签名。相比直接塞 20 个完整文件，它便宜 50 倍以上，但依然能让 AI 感知全局。为什么有效？因为大多数时候 AI 只需要知道“哪里有什么”，而不是“每一行的细节”，地图就够了，不需要卫星照片。
- 战术 3：配置铁血的排除名单。把 `build/`、`dist/`、大型 `*.log` 这类自动生成的垃圾文件，严格写入 `.gitignore` 或 IDE 的 Exclude 列表。为什么要物理切断？因为这些文件又大又没营养，AI 一旦误读一次，就是几万 Token 打水漂，还可能被里面的乱码带偏。

## 利用缓存

除了管住手少发文件，我们还需要在通信协议层面“榨干”大模型厂商的规则。

### 顺序即金钱（极致利用 Prompt Caching）

除了少发文件，还要在通信顺序上做文章。大模型的缓存机制（KV 缓存）是从头开始逐字匹配的，顺序一变，缓存就失效。

最佳实践很简单：永远把静态的大块头放在最前面，把动态的小变化放在最后面。比如系统指令、项目规约 `CLAUDE.md`、全库 API 工具定义，这些几个小时都不会变的内容固定放开头。用户的最新提问、当前报错日志这些每次都变的内容放结尾。

这样设计的好处是：占体积 80% 的静态部分，每次都能命中低价缓存，你只为新增的那 20% 付全价。顺序对了，省钱是自动发生的。

### 自动会话压缩与“逐字剔除”（Verbatim Deletion）

当对话变长触发阈值时，千万不要让 AI 去“总结历史对话”。总结听起来聪明，实则会丢掉关键细节，比如准确的文件路径和原始报错代码，一旦丢掉，AI 就会开始编造幻觉。

现代工具的做法是逐字剔除，比如 Claude Code 的 Compact 机制：它不总结，而是直接删除历史里的废话。像“你说的对，对不起，我马上改”这种道歉客套、重复生成的样板代码、来回试错的中间过程，全部删掉，只保留核心架构决策和最终的代码精髓。

为什么这样更好？因为它斩断了复利，却没有损失智商。对话瞬间瘦身，但 AI 记住的都是干货，下一次回答依然精准。

## 工具链优化

当 Agent 挂了 10 个以上工具时，光是给模型解释“每个工具怎么用”的说明书，就要吃掉几万 Token，而且每轮对话都要重发一遍。

正确做法是两招：
- 延迟加载，按需搜索： 不要一次性全量加载，让 AI 先用关键词搜索工具，用到哪个再加载哪个的详细说明。为什么？把“工具说明书”也当成上下文来剪枝，没用到的工具就不付钱。
- 语义缓存，拒绝重复查询： 对于重复的数据库或 API 查询，用 Redis 加向量检索做一层语义缓存，问题意思差不多就直接返回上次的结果。为什么？同样的查询没必要让大模型再算一遍，缓存命中就是纯赚。

如果有大批量、但不着急的任务，比如夜间 CI 自动做代码审查、给遗留代码批量补文档注释、批量生成回归测试，千万别用实时同步 API。

改用 OpenAI 或 Anthropic 的 Batch API。原理很简单：你愿意等系统在闲时处理，通常几十分钟内返回，作为交换，所有输入和输出都享受明显的价格优惠。不赶时间，就没必要付加急费。

## 极简工作流

即便不懂底层 API，身为开发者，养成以下三个习惯也能极大截断亏损：

- 护栏前置：无测试，不开 AI：有测试用例，AI 就有了靶子，通常一次就能写对。没有测试，AI 会像无头苍蝇一样瞎猜试错三四次。为什么省钱？因为你付的每一轮试错 Token，本质上都是在为“没有靶子”买单。
- 小步提交，拒绝宏大叙事：让 AI 改 50 行，验证通过就提交，再改下个 50 行。不要让它一次性重构 2000 行。为什么？大任务失败率极高，一旦跑飞，前面产生的几万个废弃 Token 全部打水漂。小步走，每步的浪费都是有上限的。
- 关闭 IDE 的“常驻自动补全”：像 Cursor 的 Tab 补全看着爽，背后是模型在疯狂发请求。如果你不是全天高强度写码，它一天能悄无声息烧掉不少费用，还全是噪音。改成按键手动触发，或者用本地 14B 开源模型接管，接近零成本，体验差不了太多。
