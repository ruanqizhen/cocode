# 环路工程（Loop Engineering）

> “流水不腐，户枢不蠹。” ——《吕氏春秋》

在 AI 辅助编程领域，技术的范式转换往往比想象中来得更快。2023 年，我们在讨论如何写出完美的提示词（Prompt Engineering）；2024 年，重点转向了为模型提供精准上下文（Context Engineering）；到了 2025 年，Harness Engineering（为 Agent 构建可靠工作环境的工程）开始火爆。

而在近期，一个更具颠覆性的概念在开发者社区引发了广泛讨论：Loop Engineering（环路工程）。

正如 Anthropic Claude Code 负责人 Boris Cherny 所言：“我不再手动给 Claude 写提示词了。我跑了一堆 Loop 去提示它，让它自己判断接下来要做什么。我的工作变成了写 Loop。” OpenClaw 创始人 Peter Steinberger 也印证了这一点：“你不应该再亲自给 Coding Agent 写提示词了。你应当设计那些能够替你去提示 Agent 的循环系统。”随后，Google 软件工程师 Addy Osmani 将这一实践方法论体系化。

本章将深度拆解 Loop Engineering 的核心理念、底层架构，以及如何用极简的代码在真实业务中落地。


## 从 Harness 到 Loop 的升维

在早期的“提示词时代”，人机协作通常是开环（Open-Loop）的：你输入 Prompt，AI 吐出代码，对话就结束了。AI 甚至不知道这段代码到底能不能跑，它没有执行环境，看不到结果。

于是验证的活儿全落在你身上：把代码复制到编辑器、运行、看到报错、再把报错信息复制回对话框、重新提问。AI 生成一次要几秒，你完成这一圈要几分钟。整个系统的效率就卡在你这一环上。人成了整个系统的瓶颈。

Agent 时代要解决的就是这件事：把这个循环交给机器自己跑。AI 写代码 → 自己执行 → 自己看到报错 → 自己修改 → 再执行，直到跑通。这就是闭环。

有意思的是，实现这个闭环的方式，正在从复杂变回简单。早期大家用的是固定工作流框架：开发者事先画好状态图，规定“第一步做什么、什么条件下走哪个分支”，把 Agent 的行为路径设计得清清楚楚。而现在越来越多的 Agent 回到了一个朴素的 Loop：不预设任何路径，只反复执行“思考 → 调用工具 → 观察结果”，让模型自己决定每一步干什么。

为什么？因为模型变强了。当模型已经能自己判断“哪里错了、下一步该怎么办”时，你精心画的那张流程图就不再是帮助，而是束缚：它把模型能走的路限制在你想到的那几条上，而任何没预料到的情况，都得回去改图。

所以这个转向不是审美之争，而是工程结论：简单的 Loop 在真实任务上跑得更好、也更好维护。

### 1. 智能重心的下放：模型变了

2024 年初，用当时最强的模型 GPT-4（128K 上下文）做 Agent，工具调用的准确率大概只有 60%。你不把流程写死，Agent 就会迷路。因此，当时的 Workflow 框架本质上是“用代码画流程图”，人类负责规划，模型负责机械执行。

但到了 2025 年，新模型的准确率大大提高，如果给它同样的任务，告诉模型目标，扔进循环。模型在循环中自己“看到”报错，自己决定怎么改。这种方式模型不再会出错，并且运行更快，代码质量更高。 智能的重心从“框架设计层”转移到了“模型推理层”。

### 2. Ralph Loop：一行 Bash 的暴力美学

2025 年，开发者 Geoffrey Huntley 仅用一行 Bash 脚本，就开发了一个完整的编程语言项目，耗费了 297 美元的 API 费用：

```bash
while :; do cat PROMPT.md | claude -p; done
```

先解释一下这行代码：

| 片段 | 含义 |
| --- | --- |
| `while :` | `:` 是 shell 里永远返回真的空命令，所以这是一个无限循环 |
| `cat PROMPT.md` | 把一个叫 `PROMPT.md` 的文件内容打印出来 |
| `\| claude -p` | 通过管道把内容喂给 Claude 命令行工具。`-p` 让它以非交互模式运行（读 stdin、输出结果、退出），不进入需要人打字的界面 |
| `done` | 回到开头，再来一遍 |

翻译成人话：反复地把同一份任务说明书交给 AI，一遍又一遍，永不停止。

为什么“重复读同一个文件”不是在做无用功？这是一个反直觉的地方。既然每次输入都一样，为什么输出不是一样的？

因为每一轮循环之间，外部环境都在发生变化。上一轮 AI 干的活：创建的源文件、跑测试留下的日志、写进 TODO 里的进度，全都留在磁盘上。下一轮它启动后， AI 会先去读这些文件，于是看到的是一个已经被推进过的项目，自然会接着往下做而不是从头开始。

所以我们也可以想想得到，在 `PROMPT.md` 文件里写的不是“请实现 XXX”这种一次性指令，而是一份长期工作守则，比如：“你的目标是实现 X。先看 `TODO.md` 了解进度，再看最近的测试输出。挑一件还没做完的事去做，做完更新 `TODO.md`。”

### 3. Harness 与 Loop 的生态位对比

Harness（基座工程）解决的是“单次做对”，而 Loop 解决的是“持续做对”。

| 维度 | Harness（基座工程） | Loop（环路工程） |
| --- | --- | --- |
| 核心目标 | 单次做对（规范动作） | 持续做对（达成目标） |
| 触发方式 | 手动启动 | 按时间、事件自动触发 |
| 执行周期 | 单次会话（Session） | 持续执行，跨会话（Cross-session） |
| 状态管理 | 存在于上下文（Context）中 | 物理固化在磁盘、文件或看板上 |
| 人类角色 | 操作者、命令下达者 | 设计者、规则制定者 |



## 核心架构

如果要让 AI Agent 进入“自动循环干活”状态，又不至于失控、重复劳动、把 Token 烧光，那么需要把 AI Agent 分成几个模块。把这个 Loop 想象成一个小团队在值班，每个架构模块负责解决一个具体的失控风险。
 

1. Automations（自动化/调度）：循环的心跳。决定“什么时候干活”。没有心跳，Loop 要么一直空转浪费 Token，要么没人叫醒它。常见做法是利用定时任务，例如“每 5 分钟检查一次”；或者利用 Webhook 事件触发（有新 PR 才跑）；或者自定义 Skill 做定时检查。`/loop` 不是 Claude Code 的内置命令，想做循环得自己用 Cron、`/tasks` 或脚本去搭。
2. Worktrees（工作树）：解决多 Agent 并行冲突。多个 Agent 同时改代码，最容易互相覆盖、冲突。Git worktree 让每个 Agent 在独立的目录和分支里工作，共享同一份提交历史，但文件系统互不干扰。在 Claude Code 里这是通过 EnterWorktree 工具或 git worktree 命令实现的。
3. Skills（技能）：固化领域知识与边界护栏。把“这个项目该怎么做、不该做什么”固化下来。比如代码规范、测试流程、禁止直接 push main 分支。Skill 让每次循环启动的 Agent 不用重新学习，直接加载同一套行为约束，减少犯错和返工。
4. Connectors / MCP（连接器）：连接外部世界的触角。Loop 不能只活在终端里。它需要读到外部世界的状态：GitHub Issue、Jira 看板、Slack 消息、CI 结果。MCP 就是统一的接入协议，让 Agent 能查询和操作这些外部系统，形成“感知-行动”闭环。
5. Sub-agents（子智能体）：实现角色分离。一个 Agent 既写代码又自己审查，很容易自我认同、放过 bug。拆成 Maker（负责写）和 Checker（负责挑刺）两个角色，Checker 独立评审，不通过就打回。这是一种轻量质量门禁，也是防止 Loop 自我欺骗的关键。
6. Memory（记忆层/状态层）：Loop 的“脊椎”。单次会话结束后，Agent 会失忆。如果没有持久化状态，下一次循环醒来会重复做已经做完的事，这就是“无限空耗 Token”的主要来源。保存记忆的方法通常很朴素：用 Markdown 文件（如 PROGRESS.md、CHANGELOG.md、TODO.md）记录“做完了什么、还剩什么、当前卡在哪里”。每次循环先读记忆，再决定要不要干活、干哪一步。


## 用 Claude Code 复刻“知识编译 Loop”

所谓“知识编译”，是借用程序员的编译概念：你每天看到的文章、灵感、聊天记录都是源代码，又乱又不能直接用。Loop 要做的，就是写一条自动流水线，把它们编译成干净、可检索、可复用的知识库。每天早晨，你收到的不是信息，而是一份简报。

### 1. 搭流水线

用目录实现“三级提纯”，不要把所有文件丢在一起。我们用三个目录强制信息分层流动：

```bash
mkdir -p inbox raw wiki scripts worktree log
touch wiki/_changelog.md raw/_registry.md log/loop-run.log CLAUDE.md
```

| 目录/文件 | 扮演的角色 | 为什么必须分开 |
| --- | --- | --- |
| `inbox/` | 收纳箱 | 任何看到的东西先扔进来，不做判断。好处是收集零负担，不会因为怕整理而放弃记录。 |
| `raw/` | 待编译区 | 只有通过初步筛选的内容才能进来。`raw/_registry.md` 记录每条素材的来源和筛选理由，方便以后追溯。 |
| `wiki/` | 成品知识库 | 只存写好的、结构化的词条。`wiki/_changelog.md` 记录每次更新了什么，这是你的版本历史。 |
| `scripts/` `log/` `worktree/` | 工具区 | `scripts` 放自动化脚本，`log` 存每次运行的日记和日报，`worktree` 是给 AI 干活用的临时隔离间。 |
| `CLAUDE.md` | 总宪法 | 告诉 Claude Code 这个项目的目标、分工和铁律，所有任务都要遵守它。 |

这样设计的好处是防止污染：半成品永远碰不到成品库。你的 wiki 不会变成第二个 inbox。

### 2. 定规则

Skill 可以理解为一个可复用的“岗位说明书”，里面写清了输入、输出和操作规范。我们不写一个万能提示词，而是拆成三个单一职责的 Skill，让 AI 每次只做一件事，幻觉和出错率会大幅下降。

* 全局约束 `CLAUDE.md`：定义全流程只有三步：分拣(triage)、编译(compile)、简报(briefing)，并规定 Maker 负责生产、Verifier 负责挑错。
* `triage.md` 分拣员：只读 `inbox/`。任务是剔除广告和水文，把有用的移入 `raw/` 并登记到 `_registry.md`，然后清空 `inbox/`。为什么要先分拣？因为 80% 的信息不值得编译，先过滤能省掉大量 token 和时间。
* `compile.md` 编译员：只读 `raw/`。任务是把零散素材写成结构化的 wiki 词条存入 `wiki/`，并在 `_changelog.md` 留痕，然后清空 `raw/`。清空的动作很关键，它保证了每条素材只被处理一次。
* `briefing.md` 简报员：只读 `log/` 和 `wiki/`。任务是生成 `log/daily-brief.md` 当日简报，并顺手检查 wiki 内是否有断裂的双向链接。它的好处是让知识产生复利：你每天只看一份报告，就能倒逼整个系统持续运转。

### 3. 防自欺

让同一个 AI 既写又审，等于自己给自己打分，一定会放水。所以我们引入角色分离：

```bash
#!/bin/bash
# 1. Maker 在隔离区写作
git worktree add worktree/maker -b maker-work
cd worktree/maker
claude -p "根据 .claude/skills/compile/SKILL.md，把 raw/ 的内容编译成 wiki 词条"

# 2. Verifier 在另一个隔离区挑错
git worktree add worktree/verifier -b verifier-work
cd worktree/verifier
claude -p "按照 CLAUDE.md 的规范，检查 wiki 词条的关联完整性和事实一致性，只输出问题清单，不要直接修改"
```

这里的 git worktree 是关键。它会创建两个物理隔离的文件夹，让 Maker 和 Verifier 看不到对方的中间过程，只能根据最终成品来评判。这种物理隔离杜绝了“自审自改”，是保证知识库长期不腐化的核心设计。

### 4. 设闹钟

最后一步是把人的意志从流程中拿掉。用系统自带的 Crontab 加 claude -p（非交互式执行）就能实现定时调度，每日早晨 6:03 自动触发全流程：

```bash
# 手动测试一次全流程是否跑通
cd /home/YOU/knowledge-base && claude -p "执行 triage -> compile -> briefing 流水线"

# 加入 Crontab，每天 6:03 自动运行，结果追加到日志
3 6 * * * cd /home/YOU/knowledge-base && claude -p "执行 triage、compile、briefing 全流程" >> log/cron-run.log 2>&1
```

选 6:03 而不是整 6 点，是为了避开系统整点任务高峰。把路径换成你的真实英文绝对路径即可。

这套系统跑起来后，效果是线性的：实测 2 个月自动过滤 200 多篇素材，沉淀 50 多个核心概念。而你每天只需要花 3 分钟看 daily-brief.md。你省下的不是整理时间，而是“决定要不要整理”的意志力。



## 安全卡点与设计铁律

把控制权交给 AI，最大的风险不是它报错，而是它静默地把错事办成。所以 Loop 里必须预埋防线：让机器能自愈小错，让人类能拦截大错，让沉默无处藏身。

### 1. 自愈闭环与 Exit Code 0 黄金法则

自愈闭环指报错后不直接停机，而是把报错现场交回给模型重试。Exit Code 0 是 Linux 的约定：程序正常结束返回 0，出错返回非 0。它是整个 Loop 的唯一红绿灯。

AI 第一次写出的代码大概率有小错，人工逐个改成本太高。正确做法是用正则表达式或 AST（抽象语法树）从日志里只提取关键报错行，比如出错文件名、行号、异常类型，再喂回模型。这样做是降噪，避免把几千行日志全塞回去导致模型抓不住重点。

只有当类型检查、Lint、测试脚本全部返回 0 时，才允许执行 git commit。否则严禁合拢。用一个机器可判断的数字代替人的感觉，杜绝了“好像没问题就提交了”的侥幸，也让自愈循环有了明确的退出条件，不会无限重试。

### 2. 人类在环 (Human-in-the-Loop, HITL) 的三道闸门

HITL 不是让你盯着 AI 的每一步，而是在三个最容易失控的位置设闸。平时放行，出事时你能在场刹车。

| 闸门 | 你在审什么 | 在防什么 | 好处 |
| --- | --- | --- | --- |
| P 计划期 Planning | 审 Agent 生成的步骤清单 | 防它大包大揽，引入你根本不需要的依赖和架构 | 把返工消灭在开工前，成本最低 |
| E 执行期 Execution | 只看 `git diff`，不看过程 | 防它越权修改无关文件，或为省事而“脑补”一个有安全漏洞的实现 | 变更可审计，你永远知道它动了哪里 |
| T 测试期 Testing | 审测试用例本身，不是只看通过率 | 防它为了“应试通过”而偷偷删掉或放宽测试用例 | 保证测试是真的在保护你，而不是在哄你 |

### 3. 设计 Loop 的三个实用原则

- 原则一：从小开始，逐步迭代：先跑通最小闭环，也就是 Cron 定时加 Skill 加 Markdown 记忆层。为什么？因为 Loop 的 bug 90% 出在衔接处，不是单个 Skill 写得好不好。先让极简链路稳定跑一周，再加外部数据源和双 Agent，你才知道问题是谁引入的。
- 原则二：Maker 不等于 Checker：让 Agent 自己审核自己，它为了走捷径，通常会直接判定“无需修改”。实测数据很残酷：自审模式下，问题被真正修复的更新率只有 5%。引入独立 Checker 后，更新转化率跃升到 30%。好处很直接：花一份算力，换来六倍的有效修正。
- 原则三：让沉默成为敌人：Loop 最危险的状态不是报错，而是卡死在后台什么都不说。所以必须设熔断：如果同一任务连续失败 3 次，立即触发 Webhook 告警（可以理解为给你的手机或群聊发一条自动通知），并在 _changelog.md 这类日志里显式写下失败原因。好处是故障永远可见，不会让你在三天后才发现系统早就停了。


## Loop 与 Skill

Skill 是单点能力，Loop 是闭环系统。 Skill 回答“这一步怎么做”，Loop 回答“目标没达成时，怎么自己发现、自己修正、再来一遍”。

### Skill 分化成了两种

- 流程型 Skill，也就是把固定步骤写死，比如“先做 A，再做 B，最后做 C”。真实业务流程充满分支和异常，固定顺序根本覆盖不了，写得越细，死得越快。这种 Skill 正在失去价值。

- 护栏型 Skill。它不再教你操作步骤，而是给你背景知识和红线，比如“绝对不能删生产数据库”“金融口径计算要注意这三类陷阱”。它从操作指南变成了参考手册。为什么这种 Skill 反而更重要？因为 Loop 越自主，越需要护栏来约束它的自由度。Loop 负责往前冲，护栏型 Skill 负责别冲下悬崖。

### 实战建议

| 建议 | 背后在防什么 | 好处是什么 |
| --- | --- | --- |
| 别再把 LangGraph 当必需品 | LangGraph 是用来画复杂流程图的编排框架，适合强合规、要人工审批的场景。对大多数任务，它是杀鸡用牛刀 | 一个 `while` 循环加一份详细 Prompt 就能跑起 Loop，代码量少 90%，调试时一眼就能看懂 |
| 写好 Prompt 胜过编排代码 | 5000 行编排代码本质是在用代码硬编码流程，流程一变就得改代码 | 5000 字的操作手册式 Prompt，把约束、边界、错误处理都写清楚，改需求只改文字，维护成本极低，效果反而更好 |
| 动手前先锁一个干净版本 | AI 进入崩坏循环的典型症状是：第一个补丁错了，它不回滚，而是在错的基础上打第二个、第三个补丁，上下文越污染越错 | 启动复杂 Loop 前先做一次 `git commit`。一旦发现胡改，直接 `git reset --hard HEAD` 一键回档，用版本控制当熔断器，比让 AI 自己“想开点”可靠得多 |
| 用最新最强的模型做设计 | 很多复杂架构是为了弥补旧模型的笨，比如拆成十步只是因为模型记不住三步 | 在 2026 年还用将就旧模型的思路做设计，就像用 DOS 思维写现代 App。先用最强模型验证上限，架构自然会变简单 |

### 从自动化到智能化

可以这样区分两者：

- 自动化：你告诉我每一步怎么做，我照做。对应的是旧的流程型 Skill。
- 智能化：你告诉我目标是什么，我自己想办法达成，错了自己改。对应的是 Loop。

所以结论很清晰：Skill 不会被 Loop 替代，而是被 Loop 收编。Skill 退化为 Loop 里的护栏和知识库，Loop 则成为新的工程主体。

这也预示了工程师角色的转变：未来的资深工程师，不再以输出多少行代码来衡量价值，而是看他能否设计出一个稳定的闭环反馈系统。写代码是体力，设计让 AI 不跑偏、错了能自愈的 Loop，才是真正的顶层能力。
