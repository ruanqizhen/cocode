# 基座工程（Harness Engineering）

> “纲举而目张。” ——《吕氏春秋》

同样的智力引擎，比如都调用 Claude 3.5 Sonnet，为什么在简陋的网页对话框里，它连 50 行代码都可能写错，而在 Claude Code 这样的终端编程代理里，它却能行云流水地自主完成整个项目，甚至自己检索资料、解决合并冲突？

这背后的根本差别不在模型，在模型身上的装备。大模型本质上只是一个估算下一个字符概率的无反馈输出机器。它拥有极高水平的代码生成能力，但它没有手脚，也没有眼睛。放在网页对话框里，它就是这种裸奔状态：它不知道你的项目有哪些文件，调不起本地编译器来验证对错，也看不到你的 Git 树现在是干净还是冲突。它只能靠猜来补全信息，猜 50 行不出错已是运气好。

要让它真正像人一样干活，就必须给它配一套由软件工程环境、工具集和控制回路构成的“机械外骨骼”。在现代 AI Agent 架构里，这套外骨骼就叫 Harness，底座框架。

如何设计、优化、操控这套外骨骼，就是本章要探讨的前沿课题：底座工程（Harness Engineering）。在未来十年，底座工程会是 AI 编程中最重要的底层技能。模型负责思考，底座决定它能走多远。

## Agent = Model + Harness

理解底座工程的起点，是业界流传最广的一个公式：

`Agent = Model + Harness`
`智能体 = 模型 + 底座框架`

它想说的是：你感受到的“智能”，只有一半来自模型权重，另一半来自模型之外的所有基础设施。换模型是换大脑，换 Harness 是换身体和工作环境，后者对实际效果的影响经常更大。

Harness 直译是马具，就是套在马身上用来驾驭马车的那套挽具。这个比喻很精准：模型就像一匹力大无穷但不受控的马，Harness 就是让它能真正拉车干活的缰绳、车架和刹车。

正如 LangChain 团队那句著名的话：“如果你不是模型，那你就是 Harness。” 意思是，在 Agent 系统里，所有不属于模型参数的东西，提示词工程、工具调用、记忆管理、任务调度，全都算 Harness。你每天调的其实大多是 Harness，而不是模型本身。

可以类比 CPU 和操作系统：单独的 CPU 通电后什么也做不了，只有套上操作系统，它才能管理内存、调度任务、变得有用。Harness 就是 AI 的操作系统。

大模型有几个天生的缺陷，Harness 的每个组件都是为补这些缺陷而存在的：

| 我们想要的行为 | 模型天生的短板，为什么会这样 | Harness 的补救方案，好处是什么 |
| --- | --- | --- |
| 能记住项目，有长期记忆 | 模型是无状态的，对话框一关就失忆，因为它只看当前窗口内的文字 | 用本地文件系统和向量数据库做外部记忆。好处是知识可以沉淀，Agent 下次还能接着上次的进度干 |
| 能动手解决复杂工程问题 | 模型只能输出文本，写出的代码跑不跑它自己不知道 | 给它 Bash 终端和代码执行工具。好处是把“死代码”变成“活验证”，跑不通就改到通为止 |
| 敢让它试错，又不怕它搞破坏 | 模型可能一本正经地输出 `rm -rf /` 这种毁灭性命令 | 用沙箱和网络隔离把它关进笼子里试。好处是既保留了自主试错的能力，又把爆炸半径锁死 |
| 对话很长也不变笨 | 模型有“迷失在中间”效应，上下文太长就会忽略中间的关键信息 | 做上下文剪枝和历史摘要压缩，也就是 `/compact`。好处是只保留关键决策，丢掉啰嗦过程，让注意力一直在线 |
| 遇到难题能死磕到底 | 模型一报错就道歉放弃，因为它没有“坚持”的机制 | 用自愈反馈循环加 Git 追踪。报错自动重跑，Git 记录每一步。好处是把一次性的回答变成了能持续攻坚的工作流，错了也能回滚重来 |

看懂这个表格，就看懂了底座工程的核心逻辑：模型负责产生可能性，Harness 负责把可能性变成可靠的结果。以后每给 Agent 加一个工具或流程，都可以问一句：这是在补模型的哪个短板？


## 底座工程与上下文工程

很多人会把这两个工程搞混，因为它们都在让模型变聪明。但记住一个分工就分清了：上下文工程解决的是“给模型看什么”，底座工程解决的是“如何让它看了之后能可靠干活”。

| | 上下文工程 Context Engineering | 底座工程 Harness Engineering |
| --- | --- | --- |
| 关注点 | 信息的纯度 | 系统的可靠性 |
| 通俗比喻 | 决定给 CPU 的内存里装什么数据 | 设计整个操作系统的调度、隔离和纠错机制 |
| 典型工作 | 挑选哪些文件塞进提示词，如何压缩历史，如何防止无关信息污染上下文 | 设计报错后是否重试，谁来校验，什么时候允许提交，失败时如何熔断 |
| 不管什么 | 不管代码跑不跑得通，不管有没有删库风险 | 不管具体哪段文字最相关，那是上下文工程的事 |

所以说它们是子集与超集：上下文工程是底座工程里面最关键的一个子系统。底座负责搭起整个“物理系统”，上下文负责保证送进大脑的信息是干净、够用、不过载的。

分不清这两层，调试时会走弯路：Agent 变笨了，你拼命改 Harness 的重试逻辑，其实问题是上下文里塞了太多垃圾信息，模型被“毒化”了。反过来，模型明明看懂了需求却反复搞坏仓库，你再怎么精简上下文也没用，缺的是一道 Exit Code 校验的门卡。

这也是一条清晰的认知升级路径，每一级都是为了解决上一级的解决不了的问题：

```text
提示词工程 Prompt Engineering
→ 关注“人类该怎么说话”
→ 解决了：让模型听懂单次指令
→ 局限：话术再好，模型还是没有记忆和手脚

          ↓

上下文工程 Context Engineering
→ 关注“模型应该知道什么”
→ 解决了：给模型恰到好处的背景信息，防止上下文腐烂和“迷失在中间”
→ 局限：看得再清楚，干活时还是可能出错且没人兜底

          ↓

底座工程 Harness Engineering
→ 关注“如何构建闭环的可靠验证系统”
→ 解决了：用工具、沙箱、反馈循环和质量门，让试错变得安全且自动
```

理解这几层，我们就能快速定位 Agent 拉胯的原因：是“说话没说清”“没给对资料”，还是“系统没有兜底”。



## 底座工程的四大核心支柱

要构建或操控一个强大的编程底座，我们必须深度拆解并设计它的四大支柱：

### 支柱一：工具链工程 (Tool Engineering)

工具是 AI 作用于物理世界的唯一“手脚”。如何定义和向大模型暴露工具，是一门精密的学问。

* 低精度工具的陷阱：在早期，很多平台粗暴地向 AI 暴露一个通用的 `execute_bash` 终端工具，让它自行输入 `sed` 或 `grep` 去改代码。这极易导致灾难，大模型很容易写错复杂的正则，或者在输出超长文件时发生截断。
* 高精度语义工具的崛起：现代顶级 Harness（如 Claude Code 或 Cursor 底座）会提供高内聚、高精度的专用语义工具。以 Claude Code 为例：
* `Read`：限制单次只读取指定行范围（支持 limit/offset），精准防范上下文被暴力撑爆。
* `Edit`：只允许精确匹配某一段特定旧字符串进行替换，规避大面积的覆盖错误（配合 replace_all 参数）。
* `Grep` / `Glob` / `Agent`：通过 ripgrep、AST 解析及子代理探索，快速定位类或变量定义的源码位置，避免 AI 漫无目的地全库漫游。



### 支柱二：沙箱与控制工程 (Sandbox & Control Engineering)

AI 编写完代码后，必须要在本地执行编译或跑通单元测试。然而，让大模型自主在电脑上运行不可靠的终端命令是极具风险的。

* 环境隔离：一个严谨的 Harness 会将 AI 的执行操作限制在隔离的沙箱（如 Docker 容器、包含白名单安全命令的 Shell）中，严防越权渗透。
* 生命周期拦截：大模型无法准确评估任务的运行耗时。如果它不慎写出了一个死循环并运行了测试，Harness 必须具备强大的底座控制力：实施自动超时阻断（Timeout），优雅杀死僵尸进程，并捕获底层的标准错误流 (stderr)。

### 支柱三：缓存与上下文编排工程 (Context Orchestrator)

大模型的上下文窗口（Context Window）是极易受到污染的“贵重资产”。

* AST 精准路由解析：当 AI 提问“如何重构这个认证中间件”时，Harness 会在后台调用 Tree-sitter 等底层工具分析语法树，自动追溯上下游调用依赖，在 AI 甚至还未察觉之前，就将相关的跨文件片段静默推入上下文。
* KV 缓存（Prompt Caching）友好设计：现代云端模型普遍支持极速提示词缓存。Harness 必须在架构上保证，投喂给模型的上下文前缀（如你的系统级规则宪法 `CLAUDE.md`）在多次对话中是绝对静态一致的。一旦前缀被频繁注入动态时间戳或随机 Session ID 污染，底层的缓存矩阵将彻底溃散，导致首字延迟（TTFT）与 API 成本飙升 10 倍以上。

### 支柱四：自愈与回滚工程 (Self-Correction Loop)

“人非圣贤，孰能无错”，大模型在复杂的重构中写出 Bug 更是家常便饭。顶级的底座决不允许把包含编译错误的脏代码直接抛给人类，而是建立了一条钢铁般的自动化自愈闭环：

1. 自动构建与验收：Harness 在代码落地后，自动调起终端执行编译或单元测试卡点。
2. 闭环自愈：若测试爆红，底座会自动截获错误日志和堆栈信息，将其清洗为高纯度的报错特征，回喂给大模型并强制其重试。
3. 物理回滚 (Git Rollback)：这是 Harness 最后的尊严底线。如果大模型重试数次后依然无法脱困，底座会果断触发底层的版本控制 API（例如执行 `git reset --hard HEAD~1` 或 `git reset --hard <clean-checkpoint>`，配合 `git clean -fd` 清理未跟踪文件），瞬间将物理世界退回到干净的初始状态，严防脏代码污染下一次的全局战略规划。



## 如何操纵底座框架

软件大师 Martin Fowler 在《面向编程智能体的 Harness》一文中提出了一个重要洞察：Harness 实际上分为内层与外层。

* 内层框架（Builder Harness）：由工具厂商（Anthropic/Google）提供的底层 AST 检索、编译环境调度等硬核能力。
* 外层框架（User Harness）：由你这个人类使用者为特定项目构建的防线。

作为日常开发者，你虽然不需要用底层代码去手撸一个内层调度器，但你必须学会操纵已有的外层底座（User Harness Engineering），通过构建引导与传感的“转向循环”（Steering Loop），来掌控 AI 军团：

| 外层底座控制机制 | 作用方向与目标 | 在实际项目中的具体工程落地 |
| --- | --- | --- |
| 引导 (Guides/前馈控制) | 行动前：防范未然，通过物理铁律引导 AI 的认知。 | 配置 `CLAUDE.md` 项目宪法；沉淀包含高频报错模式的自定义 Agent Skills 包；规定禁用危险库。 |
| 传感 (Sensors/反馈控制) | 行动后：观察输出，捕获失败，帮助 AI 建立自愈回路。 | 在 CI/CD 管道或本地 Pre-commit 中部署强类型的 TypeScript 检查、ESLint；要求 AI 进行 Exit Code 0 测试。 |

“只有引导没有传感，智能体会反复输出看起来漂亮但根本跑不通的垃圾；只有传感没有引导，智能体会在报错中无限挣扎却永远找不到正确的方向。”两者必须形成严密的物理结合。
