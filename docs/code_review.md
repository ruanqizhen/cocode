# 代码审查

> “旁观者清，当局者迷。”

即使你的本地测试全部通过，在合入 Git 主分支前，也必须经过严苛的代码质量审计与技术文档沉淀。

随着大语言模型与 AI 代理（AI Agents）全线介入开发工作流，代码生产的速度正在突破传统研发周期的极限。曾经枯燥重复的审计与文档工作，如今迎来了史无前例的效率跃迁。

然而，在人机结对开发的新纪元，代码审查（Code Review, CR）作为保证软件质量的最后一道防线，其性质正在发生根本性的变化。

传统上，我们审查的是“人类同事的想法”；现在，我们审查的往往是“AI 代理的产出”。

这带来了一个巨大的风险：表面上看起来完美无瑕的 AI 代码，往往隐藏着行为层面或安全边界上的致命缺陷。

本章将结合业界最新的工程实践，系统梳理在 AI 时代，开发者如何重塑审查心智，并安全、高效地完成质量审计、文档沉淀与技术栈的跨越式破局。



## AI 时代代码审查的双重角色

在现代开发工作流中，AI 在代码审查中扮演着两个完全不同的角色：一是作为被审查者（你审查 AI 生成的代码）；二是作为审查工具（你用 AI 审查代码）。这两者的应对策略截然不同。


当你审查 AI 生成的代码时，这是目前工程落地中最大的风险点。AI 生成的代码通常语法正确、注释清晰，甚至自带测试用例，这极易让审查者产生“虚假的安全感”并快速通过（LGTM）。面对 AI 产出的代码，你必须完成以下心智重塑：


### 默认不信任

不要把 AI 当作一个“需要指导的初级开发者”。初级开发者拥有业务上下文和最基础的责任心，而 AI 没有。

- 传统思维：“这代码的逻辑和语法看起来合理吗？”
- AI 时代思维：“这代码做出了什么假设？这些假设在极端情况下安全吗？”

### 审查“行为”而非“语法”

AI 极少犯低级语法错误，它的问题往往出在行为逻辑上。不要把时间浪费在变量命名或代码风格（这些应交给 Linter），而是把精力集中在：状态转换、并发处理、错误重试机制以及数据验证。像攻击者一样在脑海中执行代码：AI 倾向于优化“快乐路径”（Happy Path），而攻击者专找非线性的极端路径。

### 严守身份验证与安全边界

AI 在处理安全边界时经常“和稀泥”。例如，它可能会将权限检查放在 UI 层而不是后端服务器逻辑中，或者轻信客户端传入的状态标识，甚至在无关操作间复用会话状态。对任何涉及权限（Auth）、状态流转或支付的 AI 代码，必须进行人工的深度安全审查。

### 索要证据，而非解释

AI 非常擅长用看似严谨的逻辑“解释”为什么它的代码是安全的。永远不要相信它的解释。 如果代码涉及高风险操作，要求 AI 提供具体的证据——例如证明边界条件被妥善处理的测试用例，或者动态验证的日志。没有提供证据的代码，一律视为未完成的代码。



## 构建自动化审计流水线

明确了如何防范 AI 的隐患后，我们就可以转换身份，将 AI 作为极其强大的审查工具。利用自动化审查机器人（如 CodeRabbit 或 GitHub Copilot Code Review），我们可以在合并代码前设立第一道智能化防线，让 AI 自动检查死代码、安全反模式和未处理异常，让人类审查者专注于业务逻辑与架构设计。

### 注入审查上下文与限制 PR 大小

AI 审查器如果不知道你的业务规则，就会产生大量无用的“噪音”建议。

注入上下文：在代码库根目录维护 `CLAUDE.md`、`AGENTS.md` 或 `.cursor/rules/*.mdc` 文件（旧版 `.cursorrules` 已标记为 Legacy），明确列出团队的架构约定（例如：“在审查 API 路由时，必须检查是否调用了 `requireAuth` 中间件”）。这样 AI 就能根据你的特定规则进行精准审查。

限制 PR 规模：AI 和人类一样，面对一个包含 50 个文件、2000 行修改的巨大 Pull Request（PR）时，也会陷入“认知过载”。强制规定 PR 的修改体积（例如不超过 400 行代码），能让 AI 给出更深入、准确的逻辑推演，而不是泛泛的语法建议。

### GitHub Action 自动 Code Review

每次团队成员发起 PR 时，我们可以通过 CI/CD 流水线自动唤起大模型 API 执行增量代码审查：

```yaml
# .github/workflows/ai-review.yml

name: AI Code Reviewer

on:
  pull_request:
    types: [opened, synchronize]

jobs:
  review:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout Code
        uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Run AI Reviewer
        # 注意：coderabbitai/ai-pr-reviewer 参数以官方文档为准，旧版 system_message 参数已变更
        # 建议固定版本而非 @latest，并参考官方最新输入参数
        uses: coderabbitai/ai-pr-reviewer@v1
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
        with:
          language: zh-CN
          # 额外审查指令（如支持）
          extra_instructions: |
            你是一名极致苛刻的资深系统架构审查专家。
            请分析 Pull Request 的 Git Diff，重点审查：
            1. 是否存在硬编码 API Key / Secret
            2. 是否存在 N+1 查询或缺失事务
            3. 是否存在未捕获异常或隐式类型问题
            请给出 GitHub 评论级反馈
```



### 本地审计 System Prompt
如果你在本地使用 Cursor Chat 或 Cline 对重构模块执行手动审查，请务必使用以下高度结构化、高强度的代码质量审计 System Prompt，以充分榨干大模型的审查智商：

```markdown
# Role
你是一名精通软件工程质量学派的代码审计官。

# Task
审计 Git Diff，找出架构隐患、坏味道与性能问题。

# Audit Dimensions

## 1. Reliability
Null、安全边界、资源释放问题

## 2. Performance
O(N²)、内存泄漏、IO 阻塞

## 3. Maintainability
函数过长、嵌套过深、命名模糊

## 4. Security
SQL 注入、XSS、敏感信息泄露

# Output Format

- 🔴 Critical Issues
- ⚠️ Suggestions
- 🟢 Refactored Code
```



## 自动化文档与变更日志

编写文档曾是程序员最讨厌的“苦力活”，导致许多项目最后都变成了没有任何说明的秘密黑盒。大模型作为极其出色的自然语言整理大师，能够将冰冷的代码瞬间凝练为极具阅读体验的精美文档。

- 结构化代码注释生成（TSDoc / JSDoc）：不要再手动敲击繁琐的注释了。选中复杂的类或函数，使用 IDE 快捷键唤醒 AI：“使用 JSDoc / TSDoc 规范，为此函数自动生成详尽的接口注释，详细说明参数类型、返回值、可能抛出的异常，并提供一个经典的用法示例。”

- API 交互文档自动喷涌：只需提供后端路由定义，大模型可以分秒级吐出完美符合 OpenAPI 3.0 标准的 YAML 或 JSON 格式定义，直接导入 Swagger UI 或 Postman 中无缝展示与调试。

- 高可读性的变更日志（Changelog）：发布版本前，将本周的 Git Commit 记录喂给 AI，彻底告别流水账式的提交记录：“请对本周的 Commit 历史进行归纳整理，过滤掉琐碎的修改，提炼出一份面向用户的、格式漂亮的 Release Notes。分类包含：🚀 New Features, 🐛 Bug Fixes, ⚡ Performance Upgrades。”


## 跨技术栈映射（Paradigm Mapping）

有了坚实的代码审查防线和自动化的文档兜底，开发者就可以释放出更多精力去拓宽能力边界。我们经常会遇到被紧急抽调去写不熟悉语言的状况（例如：写惯了 Java 的你被拉去写 Go/Rust，或是熟悉 React 的你必须接管一个 Svelte 项目）。

此时，大模型不仅是代码审查员，更是你的全能语言翻译器和破壁先锋。我们可以利用范式映射对照表 (Paradigm Mapping) 快速攻克技术壁垒：



| 开发诉求 | ☕ Java Spring Boot 经典模式 | 🐹 Go Gin & Gorm 对应范式 | AI 破壁伴写指令（Prompt 示例） |
|----------|-----------------------------|----------------------------|--------------------------------|
| 路由定义 | 使用 `@RestController` 和 `@GetMapping` 注解 | 使用 `r := gin.Default()` 后调用 `r.GET("/path", handler)` | “我熟悉 Spring 的注解路由。请把这段 Java Controller 翻译为使用 Go Gin 规范的 handler 函数，保持入参绑定与错误响应一致。” |
| 依赖注入 | 使用 `@Autowired` 容器自动装配 | 显式进行结构体初始化与指针注入 `service := &UserService{db: gormDB}` | “请向我解释 Go 语言中如何不使用 IoC 容器，而是通过结构体构造函数显式进行依赖注入。” |
| 数据访问 | 继承 `JpaRepository<User, Long>` 接口 | 使用 `db.Where("email = ?", email).First(&user)` 链式调用 | “请将这段 Spring Data JPA 的查询方法翻译为符合 Gorm 规范的 Go 数据库查询操作。” |



通过这套映射法，你可以在极短时间内把已有语言的工程心智直接投射到新框架中。配合 AI 的语法校验与流水线审查，即使面对完全陌生的技术栈，也能在一周内实现无障碍的高质量业务交付。

## 安全与责任的最终归属

无论是利用 AI 生成代码、审查代码、沉淀文档，还是跨越技术栈，有一条底线永远不能突破：代码的责任归属。

AI 改变代码的速度已经远远超过了传统审查周期的极限。当生产环境出现宕机或发生数据泄露时，你绝不能对客户或老板辩解说：“这是 AI 写的”。

明确所有权：代码仓库中的每一行 AI 生成代码，一旦合入主分支，都必须有一个明确的人类负责人。你合并了它，你就要对它负责。

独立的安全门禁：AI 代码审查绝对不能替代传统的 SAST（静态应用安全测试）和依赖项扫描。安全检查必须是独立、客观、无情且每次 CI 构建必跑的。


在 AI 时代，代码审查与管控的核心不再仅仅是“找 Bug”，而是“验证系统行为与守护系统边界”。保持敬畏与怀疑，善用自动化防线，明确责任归属，这是防止 AI 生成代码演变成巨大技术债务、构筑个人终极技术护城河的唯一途径。
