# Code Review

> "Sometimes you can't see the wood for the trees." — English Proverb

Even if all your local tests pass, before merging into the main Git branch, it must undergo strict code quality auditing and technical documentation sedimentation.

With the full intervention of Large Language Models and AI Agents in the development workflow, the speed of code production is breaking the limits of traditional R&D cycles. Once boring and repetitive auditing and documentation work has now ushered in an unprecedented efficiency leap.

However, in the new era of human-machine pair development, Code Review (CR), as the last line of defense ensuring software quality, its nature is undergoing a fundamental change.

Traditionally, we reviewed "the ideas of human colleagues"; now, we often review "the output of AI agents."

This brings a huge risk: AI code that seems flawless on the surface often hides fatal flaws at the behavioral level or security boundaries.

This chapter will combine the latest engineering practices in the industry to systematically organize how developers in the AI era can reshape their reviewing mindset, and safely and efficiently complete quality auditing, documentation sedimentation, and leapfrog breakthroughs in the technology stack.



## The Dual Role of Code Review in the AI Era

In modern development workflows, AI plays two completely different roles in code review: one as the reviewee (you review the code generated by AI); the other as the review tool (you use AI to review code). The coping strategies for these two are completely different.


When you review code generated by AI, this is currently the biggest risk point in engineering implementation. AI-generated code usually has correct syntax, clear comments, and even comes with test cases, which easily gives reviewers a "false sense of security" and leads them to quickly approve it (LGTM). Faced with AI-produced code, you must complete the following mindset reshaping:


### Default Distrust

Do not treat AI as a "junior developer needing guidance." Junior developers have business context and the most basic sense of responsibility, whereas AI does not.

- Traditional mindset: "Does the logic and syntax of this code look reasonable?"
- AI era mindset: "What assumptions does this code make? Are these assumptions safe under extreme conditions?"

### Review "Behavior" rather than "Syntax"

AI rarely makes low-level syntax errors; its problems usually lie in behavioral logic. Do not waste time on variable naming or code style (these should be handed over to Linters), but focus your energy on: state transitions, concurrent processing, error retry mechanisms, and data validation. Execute the code in your mind like an attacker: AI tends to optimize for the "Happy Path," while attackers specialize in finding non-linear extreme paths.

### Strictly Guard Authentication and Security Boundaries

AI often "muddles through" when handling security boundaries. For example, it might put permission checks in the UI layer instead of backend server logic, or blindly trust state identifiers passed in from the client, or even reuse session state between unrelated operations. For any AI code involving Authentication (Auth), state transition, or payments, a deep manual security review must be conducted.

### Demand Evidence, Not Explanations

AI is very good at using seemingly rigorous logic to "explain" why its code is safe. Never believe its explanations. If the code involves high-risk operations, ask the AI to provide concrete evidence—for example, test cases proving that boundary conditions are properly handled, or dynamically verified logs. Code without evidence is uniformly considered unfinished code.



## Building an Automated Audit Pipeline

After clarifying how to guard against AI's hidden dangers, we can switch roles and use AI as an extremely powerful reviewing tool. Using automated review bots (such as CodeRabbit or GitHub Copilot Code Review), we can set up a first intelligent line of defense before merging code, letting AI automatically check for dead code, security anti-patterns, and unhandled exceptions, allowing human reviewers to focus on business logic and architectural design.

### Injecting Review Context and Limiting PR Size

If an AI reviewer does not know your business rules, it will generate a lot of useless "noise" suggestions.

Inject context: Maintain an `AGENTS.md` or `.cursorrules` file in the root directory of the codebase to explicitly list the team's architectural conventions (for example: "When reviewing API routes, you must check whether the `requireAuth` middleware is called"). This way, AI can perform precise reviews based on your specific rules.

Limit PR scale: Just like humans, AI facing a massive Pull Request (PR) containing 50 files and 2000 lines of modifications will also fall into "cognitive overload." Forcing a limit on the modification volume of PRs (e.g., no more than 400 lines of code) allows AI to provide deeper and more accurate logical deductions, rather than generic syntax suggestions.

### GitHub Action Automated Code Review

Every time a team member initiates a PR, we can automatically wake up the large model API through the CI/CD pipeline to perform incremental code review:

```yaml
# .github/workflows/ai-review.yml

name: AI Code Reviewer

on:
  pull_request:
    types: [opened, synchronize]

jobs:
  review:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout Code
        uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Run AI Reviewer
        uses: coderabbitai/ai-pr-reviewer@latest
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
          OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
        with:
          debug: false

          system_message: |
            You are an extremely demanding senior system architecture review expert.
            Please analyze the Git Diff of the Pull Request, focusing on:

            1. Are there any hardcoded API Keys / Secrets?
            2. Are there N+1 queries or missing transactions?
            3. Are there unhandled exceptions or implicit typing issues?

            Please provide GitHub comment-level feedback.
```

## Automated Documentation and Changelogs

Writing documentation was once the "drudgery" that programmers hated most, leading many projects to eventually become undocumented secret black boxes. As an extremely outstanding natural language organization master, large models can instantly condense cold code into exquisite documentation with an excellent reading experience.

- Structured Code Comment Generation (TSDoc / JSDoc): Stop typing tedious comments manually. Select complex classes or functions, use IDE shortcuts to wake up the AI: "Using JSDoc / TSDoc specifications, automatically generate detailed interface comments for this function, detailing parameter types, return values, exceptions that may be thrown, and providing a classic usage example."

- Automatic Spouting of API Interactive Documentation: By simply providing backend route definitions, large models can spit out YAML or JSON format definitions that perfectly conform to the OpenAPI 3.0 standard in seconds, which can be directly imported into Swagger UI or Postman for seamless display and debugging.

- Highly Readable Changelogs: Before publishing a version, feed this week's Git Commit records to the AI to completely bid farewell to unorganized commit logs: "Please summarize and organize this week's Commit history, filter out trivial modifications, and extract a user-facing, beautifully formatted Release Notes. Categories include: 🚀 New Features, 🐛 Bug Fixes, ⚡ Performance Upgrades."


## Paradigm Mapping

With a solid code review defense line and automated documentation as a safety net, developers can free up more energy to broaden their capability boundaries. We often encounter situations where we are urgently transferred to write in an unfamiliar language (e.g., you are used to writing Java but are pulled to write Go/Rust, or you are familiar with React but must take over a Svelte project).

At this time, large models are not only code reviewers, but also your all-around language translator and wall-breaking pioneer. We can use Paradigm Mapping to quickly overcome technical barriers:



| Dev Need | ☕ Java Spring Boot Classic Pattern | 🐹 Go Gin & Gorm Corresponding Paradigm | AI Wall-Breaking Co-pilot Prompt Example |
|----------|-----------------------------|----------------------------|--------------------------------|
| Route Definition | Using `@RestController` and `@GetMapping` annotations | Using `r := gin.Default()` then calling `r.GET("/path", handler)` | "I am familiar with Spring's annotation routing. Please translate this Java Controller into a handler function using the Go Gin specification, keeping the input parameter binding and error response consistent." |
| Dependency Injection | Using `@Autowired` container auto-wiring | Explicitly performing struct initialization and pointer injection `service := &UserService{db: gormDB}` | "Please explain to me how to explicitly perform dependency injection via struct constructors in Go without using an IoC container." |
| Data Access | Inheriting `JpaRepository<User, Long>` interface | Using `db.Where("email = ?", email).First(&user)` chained calls | "Please translate this Spring Data JPA query method into a Go database query operation conforming to the Gorm specification." |



Through this mapping method, you can directly project your existing engineering mindset of a language into a new framework in a very short time. Paired with AI's syntax verification and pipeline review, even when facing a completely unfamiliar technology stack, you can achieve barrier-free, high-quality business delivery within a week.

## The Ultimate Attribution of Security and Responsibility

Whether it is using AI to generate code, review code, sediment documentation, or cross technology stacks, there is one bottom line that can never be broken: the attribution of code responsibility.

The speed at which AI changes code has far exceeded the limits of the traditional review cycle. When production environments crash or data leaks occur, you absolutely cannot justify it to clients or bosses by saying, "AI wrote this."

Clarify ownership: Every line of AI-generated code in the code repository must have a clear human owner once it is merged into the main branch. You merged it, you are responsible for it.

Independent security gates: AI code review can absolutely not replace traditional SAST (Static Application Security Testing) and dependency scanning. Security checks must be independent, objective, ruthless, and run on every CI build.


In the AI era, the core of code review and control is no longer just "finding Bugs," but "verifying system behavior and guarding system boundaries." Maintaining awe and skepticism, making good use of automated defense lines, and clarifying the attribution of responsibility is the only way to prevent AI-generated code from evolving into massive technical debt and to build your ultimate personal technical moat.
