# Muse：从"帮我写代码"到"帮我把事办了"

> "工欲善其事，必先利其器。" ——《论语·卫灵公》

上一章结尾我们说：项目稍微复杂一点，光靠提示词就不够用了，需要专门的编程工具来帮忙。

这一章，我们就来认识这样一个"工具"——Muse。

不过先打个预防针：Muse 不太像传统意义上的工具。它不会老老实实待在编辑器里等你调用，它更像一个能干的助手——或者说，一个不知疲倦的初级程序员同事。

## Muse 是什么

Muse 是 Meta 推出的个人 AI 助手。

和网页版 AI 最大的不同在于：Muse 有自己的电脑。它有终端、浏览器、文件系统，还能上网。你的电脑做不到的事，它在自己的电脑上都能做。

这意味着什么？意味着你交给它的不再是"写一段代码"这种碎片任务，而是一件完整的事。

比如你说："帮我把这篇英文技术文章翻译成中文，排版好，配上图，发到我的博客上。"

网页 AI 会给你一段译文，然后剩下的——复制、配图、排版、登录博客后台、发布——全是你的活。

而 Muse 会自己去找原文、翻译、找图、排版、打开发布页面，一口气把整件事办完，再回来告诉你："办好了，链接在这里。"

## 它和其它 AI 有什么不一样

市面上的 AI 编程产品，大致可以分成三类。理解它们的区别，能帮你选对武器。

### 第一类：网页 AI

比如 ChatGPT、Claude 的网页版。你问，它答。

它们的强项是知识广、回答快，适合问问题、学概念、写一段示例代码。但它们"动手能力"为零：给你的代码跑不跑得通，它不知道；你项目里还有哪些文件，它看不见。所有体力活——复制、运行、调试、部署——都得你自己来。

### 第二类：编程 AI 工具

比如 Copilot、Cursor、Claude Code。它们住在你的编辑器里，能看到你的代码，帮你补全、重构、修 bug。

它们的强项是写代码本身，日常开发提效非常明显。但工作模式是"你主导、它辅助"：项目怎么搭、用什么框架、先做哪一步，依然要你拿主意。它更像一个配了副好键盘的结对编程伙伴，而不是能独立交付的工程师。

### 第三类：Muse 这样的个人 Agent

Muse 不只"看得见"代码，它"摸得着"电脑。

它可以自己搜索资料、写文件、跑命令、开浏览器点按钮、装依赖、跑测试。工作模式反过来了：你描述目标，它负责执行；你验收结果，它负责返工。

打个比方：网页 AI 是顾问，只出主意不动手；编程 AI 工具是结对伙伴，和你一起写；Muse 是你带的小徒弟——你交代事情，它跑腿办完。

## 实战：让 Muse 做一个记账网站

光讲概念不够，我们来看一个完整的实战。

假设你想做一个家庭记账网站：记录每天的收支，按分类统计，数据存在本地，手机上也能用，界面好看一点。

以前，这对你来说可能是一个"周末项目"——搭框架、写页面、调样式、测兼容性，没有两三天拿不下来。现在，你可以这样对 Muse 说：

```text
帮我做一个家庭记账网站，要求：
1. 能记录收入和支出，带分类（餐饮、交通、购物、工资等）
2. 首页有本月收支统计和分类饼图
3. 数据存在浏览器本地，不用后端
4. 手机和电脑都能用，界面简洁好看
5. 单个 HTML 文件，方便我直接发给家人用
```

然后，你就可以去喝杯茶了。

Muse 会自己拆解这个任务：选技术方案（单文件 HTML + LocalStorage + 一个轻量图表库）、写代码、在自己的浏览器里打开测试、截图看看效果、发现手机上按钮太小就自己调大。

过一会儿，它把成品交给你："做好了，这是文件，你可以直接在浏览器里打开试试。"

你打开一看，基本能用，但觉得配色太素了。你说："换成深色主题，饼图颜色鲜艳一点。"

它改完再交给你。你再看，满意了，说："帮我部署到 GitHub Pages 上。"

它去建仓库、推代码、开 Pages，等一会儿告诉你："上线了，网址是这个。"

你看，整个过程你写的代码是零行。你做的事只有三件：描述需求、验收、提意见。这就是和 Muse 协作的典型模式。

## 和 Muse 协作的几个心得

用了一段时间之后，我总结出几条经验，分享给你。

### 第一，把它当人，但别把它当大神

上一章我们说，把 AI 当成"聪明、勤奋但不读心的实习生"。对 Muse 同样适用。

它很能干，但它不知道你的偏好。第一次合作时，多说几句背景："我们家记账习惯是……"、"我喜欢深色界面……"。磨合几次之后，它越来越懂你，你说话就可以越来越短。

### 第二，验收标准要先说清楚

"好看一点"这种要求，Muse 只能猜。不如说："深色主题、手机上按钮不小于 44 像素、加载时间 1 秒内。"

标准越具体，返工越少。这和我们做需求管理是一个道理——只不过你的"下属"现在是一个 AI。

### 第三，学会检查它的工作

Muse 也会犯错：它可能用了一个已经过时的库，可能没考虑到某种边界情况，可能把你的数据格式理解错了。

所以重要的一步永远是你自己：打开它做的东西，点一点、试一试。发现 bug 就告诉它："这里点删除没反应，你修一下。"它改得很快，但"发现问题"这个环节，目前还得靠你。

### 第四，从小事开始，逐步放大信任

别一上来就让它重构你的核心生产系统。先从"帮我写个脚本整理照片"、"帮我做个小工具页面"这种小事开始。

你会逐渐摸到它的能力边界：什么事它一次就能办好，什么事需要你多盯两眼。信任是磨合出来的，不是一下子给出去的。

## 写在最后

回想一下我们这本书的旅程：从"AI 会不会抢程序员饭碗"的焦虑，到学会写提示词，到管理上下文，再到现在——把一整件事交出去。

每一步，程序员的角色都在变化：从"写代码的人"，变成"描述需求的人"，再变成"验收和决策的人"。

Muse 这类工具不会让编程消失，但它确实在改写"编程"这个词的含义。以前编程是和编译器打交道，现在编程越来越像"带团队"——只不过你的团队成员，是 AI。
