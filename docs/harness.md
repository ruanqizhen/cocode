# 底座工程（Harness Engineering）

> “纲举而目张。” ——《吕氏春秋》

同样的智力引擎，比如都调用 Claude 3.5 Sonnet，为什么在简陋的网页对话框里，它连 50 行代码都可能写错，而在 Claude Code 这样的终端编程代理里，它却能行云流水地自主完成整个项目，甚至自己检索资料、解决合并冲突？

这背后的根本差别不在模型，在模型身上的装备。大模型本质上只是一个估算下一个字符概率的无反馈输出机器。它拥有极高水平的代码生成能力，但它没有手脚，也没有眼睛。放在网页对话框里，它就是这种裸奔状态：它不知道你的项目有哪些文件，调不起本地编译器来验证对错，也看不到你的 Git 树现在是干净还是冲突。它只能靠猜来补全信息，猜 50 行不出错已是运气好。

要让它真正像人一样干活，就必须给它配一套由软件工程环境、工具集和控制回路构成的“机械外骨骼”。在现代 AI Agent 架构里，这套外骨骼就叫 Harness，底座框架。

如何设计、优化、操控这套外骨骼，就是本章要探讨的前沿课题：底座工程（Harness Engineering）。在未来十年，底座工程会是 AI 编程中最重要的底层技能。模型负责思考，底座决定它能走多远。

## Agent = Model + Harness

理解底座工程的起点，是业界流传最广的一个公式：

`Agent = Model + Harness`
`智能体 = 模型 + 底座框架`

它想说的是：你感受到的“智能”，只有一半来自模型权重，另一半来自模型之外的所有基础设施。换模型是换大脑，换 Harness 是换身体和工作环境，后者对实际效果的影响经常更大。

Harness 直译是马具，就是套在马身上用来驾驭马车的那套挽具。这个比喻很精准：模型就像一匹力大无穷但不受控的马，Harness 就是让它能真正拉车干活的缰绳、车架和刹车。

正如 LangChain 团队那句著名的话：“如果你不是模型，那你就是 Harness。” 意思是，在 Agent 系统里，所有不属于模型参数的东西，提示词工程、工具调用、记忆管理、任务调度，全都算 Harness。你每天调的其实大多是 Harness，而不是模型本身。

可以类比 CPU 和操作系统：单独的 CPU 通电后什么也做不了，只有套上操作系统，它才能管理内存、调度任务、变得有用。Harness 就是 AI 的操作系统。

大模型有几个天生的缺陷，Harness 的每个组件都是为补这些缺陷而存在的：

| 我们想要的行为 | 模型天生的短板，为什么会这样 | Harness 的补救方案，好处是什么 |
| --- | --- | --- |
| 能记住项目，有长期记忆 | 模型是无状态的，对话框一关就失忆，因为它只看当前窗口内的文字 | 用本地文件系统和向量数据库做外部记忆。好处是知识可以沉淀，Agent 下次还能接着上次的进度干 |
| 能动手解决复杂工程问题 | 模型只能输出文本，写出的代码跑不跑它自己不知道 | 给它 Bash 终端和代码执行工具。好处是把“死代码”变成“活验证”，跑不通就改到通为止 |
| 敢让它试错，又不怕它搞破坏 | 模型可能一本正经地输出 `rm -rf /` 这种毁灭性命令 | 用沙箱和网络隔离把它关进笼子里试。好处是既保留了自主试错的能力，又把爆炸半径锁死 |
| 对话很长也不变笨 | 模型有“迷失在中间”效应，上下文太长就会忽略中间的关键信息 | 做上下文剪枝和历史摘要压缩，也就是 `/compact`。好处是只保留关键决策，丢掉啰嗦过程，让注意力一直在线 |
| 遇到难题能死磕到底 | 模型一报错就道歉放弃，因为它没有“坚持”的机制 | 用自愈反馈循环加 Git 追踪。报错自动重跑，Git 记录每一步。好处是把一次性的回答变成了能持续攻坚的工作流，错了也能回滚重来 |

看懂这个表格，就看懂了底座工程的核心逻辑：模型负责产生可能性，Harness 负责把可能性变成可靠的结果。以后每给 Agent 加一个工具或流程，都可以问一句：这是在补模型的哪个短板？


## 底座工程与上下文工程

很多人会把这两个工程搞混，因为它们都在让模型变聪明。但记住一个分工就分清了：上下文工程解决的是“给模型看什么”，底座工程解决的是“如何让它看了之后能可靠干活”。

| | 上下文工程 Context Engineering | 底座工程 Harness Engineering |
| --- | --- | --- |
| 关注点 | 信息的纯度 | 系统的可靠性 |
| 通俗比喻 | 决定给 CPU 的内存里装什么数据 | 设计整个操作系统的调度、隔离和纠错机制 |
| 典型工作 | 挑选哪些文件塞进提示词，如何压缩历史，如何防止无关信息污染上下文 | 设计报错后是否重试，谁来校验，什么时候允许提交，失败时如何熔断 |
| 不管什么 | 不管代码跑不跑得通，不管有没有删库风险 | 不管具体哪段文字最相关，那是上下文工程的事 |

所以说它们是子集与超集：上下文工程是底座工程里面最关键的一个子系统。底座负责搭起整个“物理系统”，上下文负责保证送进大脑的信息是干净、够用、不过载的。

分不清这两层，调试时会走弯路：Agent 变笨了，你拼命改 Harness 的重试逻辑，其实问题是上下文里塞了太多垃圾信息，模型被“毒化”了。反过来，模型明明看懂了需求却反复搞坏仓库，你再怎么精简上下文也没用，缺的是一道 Exit Code 校验的门卡。

这也是一条清晰的认知升级路径，每一级都是为了解决上一级的解决不了的问题：

```text
提示词工程 Prompt Engineering
→ 关注“人类该怎么说话”
→ 解决了：让模型听懂单次指令
→ 局限：话术再好，模型还是没有记忆和手脚

          ↓

上下文工程 Context Engineering
→ 关注“模型应该知道什么”
→ 解决了：给模型恰到好处的背景信息，防止上下文腐烂和“迷失在中间”
→ 局限：看得再清楚，干活时还是可能出错且没人兜底

          ↓

底座工程 Harness Engineering
→ 关注“如何构建闭环的可靠验证系统”
→ 解决了：用工具、沙箱、反馈循环和质量门，让试错变得安全且自动
```

理解这几层，我们就能快速定位 Agent 拉胯的原因：是“说话没说清”“没给对资料”，还是“系统没有兜底”。


## 底座工程的四大核心支柱

底座不是一个东西，而是四套机制的组合：给它好用的手，关进安全的笼子，保证大脑不被污染，最后允许它犯错但能复原。

### 支柱一：工具链

早期很多平台偷懒，直接给 AI 一个万能的 `execute_bash`，让它自己拼 `sed` 或 `grep` 去改代码。这非常危险，模型很容易写错正则，或者一次输出几万行把上下文撑爆，一次手滑就是灾难。

优秀的 Harness 会使用高精度语义工具，每个工具只做一件事，把自由度锁死。以 Claude Code 为例：

* `Read`：每次只读指定行范围，支持 limit 和 offset。防止 AI 一言不合就读整个文件，把宝贵的上下文窗口暴力撑爆。
* `Edit`：必须精确匹配到某段旧字符串才允许替换。避免 AI 自作主张大面积覆盖，改错一个字符也能被卡住。
* `Grep` / `Glob` / `Agent`：底层用 ripgrep 和 AST 语法解析去定位定义，或者派子代理去探索。让 AI 直接拿到“这个类在哪定义的”，而不是让它像无头苍蝇一样全库漫游，省时间也省 token。

工具越“笨”、限制越多，AI 反而越稳。因为它犯错的空间被工程手段提前堵死了。

### 支柱二：沙箱与控制

代码写完必须在本地编译和跑测试，但让 AI 在你的电脑上随意跑终端命令，风险极高。一个死循环测试就能卡死你的机器，一条删库命令就能造成不可逆损失。

现在的做法有两层：
* 环境隔离：把 AI 的执行限制在沙箱里，比如 Docker 容器或只允许白名单命令的安全 Shell。它的破坏力再大，也翻不出这个笼子。
* 生命周期拦截：模型自己判断不好任务要跑多久。Harness 必须在底座层面有控制力：自动超时阻断，优雅杀掉僵尸进程，并捕获底层的标准错误流送回去分析。

你敢放手让 AI 自主试错，因为最坏情况只是沙箱里的一次失败，而不是你主机的一次灾难。

### 支柱三：缓存与上下文编排

模型的上下文窗口是贵重且极易被污染的资产，这个支柱专门负责“给大脑喂什么、怎么喂最省”。

* AST 精准路由：当你问“如何重构这个认证中间件”，Harness 会在后台用 Tree-sitter 分析语法树，自动找到它的上下游调用，把相关的跨文件片段静默推入上下文。为什么？让 AI 在开口前就看到全貌，不用它自己去猜去找，回答一次就准。
* 缓存友好设计：现在的云端模型都支持提示词缓存，前缀相同就能命中缓存，首字延迟和成本都很低。Harness 必须保证每次投喂的前缀是静态一致的，比如系统规则 `CLAUDE.md` 永远放在最前面一字不差。一旦你在前缀里塞了动态时间戳或随机 Session ID，缓存就会彻底失效，实测延迟和 API 成本能飙升 10 倍以上。

同样的模型，喂得准、喂得稳，不仅答得更好，还更快更便宜。

### 支柱四：自愈与回滚

模型写出 Bug 是家常便饭，顶级底座的原则是：绝不把带着编译错误的脏代码直接丢给人类。

1.  自动验收：代码一落地，Harness 自动调起编译或单元测试，先过一遍卡点。
2.  闭环自愈：如果测试变红，底座自动截获日志和堆栈，清洗成高纯度的报错特征，再喂回给模型强制重试。为什么要清洗？因为原始日志太啰嗦，模型抓不住重点。
3.  物理回滚：这是最后的尊严底线。如果重试几次还救不回来，底座会果断调用版本控制，比如执行 `git reset --hard` 回到干净的检查点，并用 `git clean -fd` 清掉未跟踪文件。为什么必须这么狠？防止这次的脏代码污染下一次的全局规划，长痛不如短痛。

把“人来擦屁股”变成了“系统自己兜底”。AI 可以大胆冲，因为它知道冲垮了有人能一键复原。



## 如何操纵底座框架

软件大师 Martin Fowler 在《面向编程智能体的 Harness》里点破了一个关键分层：Harness 其实有内外两层，你不需要两层都造。

* 内层框架 Builder Harness：由 Anthropic、Google 这样的工具厂商提供。比如底层的 AST 检索、编译环境调度、模型调用优化，这些硬核能力轮不到你操心，你也造不出来。
* 外层框架 User Harness：由你为自己的项目亲手搭建的防线。这才是日常开发者真正的主战场。

你不需要手撸一个调度器，但你必须学会操纵外层底座。核心方法是构建一个“转向循环”（Steering Loop），像开车一样不断微调方向，掌控你的 AI 军团。它由两个方向的机制组成：

| 控制机制 | 作用时机与目标 | 在项目里具体怎么做 | 为什么必须做 |
| --- | --- | --- | --- |
| 引导 Guides，前馈控制 | 行动前：防范未然，提前告诉 AI 什么能做、什么绝对不能做 | 写好 `CLAUDE.md` 项目宪法；沉淀常见报错模式的自定义 Skills 包；明确禁用危险库和危险命令 | 没有引导，AI 就像没看过交规的司机，方向一开始就是错的 |
| 传感 Sensors，反馈控制 | 行动后：观察输出，捕获失败，帮 AI 建立自愈能力 | 在本地 Pre-commit 或 CI/CD 里强制跑 TypeScript 类型检查、ESLint、单元测试，要求必须 Exit Code 0 才能过 | 没有传感，AI 就像闭着眼睛开车，撞墙了也不知道回头 |

为什么两者缺一不可？

只有引导没有传感，AI 会反复输出看起来很漂亮但根本跑不通的代码，因为它从未被真实验证打过脸。只有传感没有引导，AI 会在报错里无限挣扎、反复试错，因为它从一开始就缺少正确的方向和约束。

真正的外层底座工程，就是让引导和传感形成严密咬合：引导让 AI 少犯错，传感让犯了的错能被抓住、被修正。修好一次，就把这次的教训沉淀回引导里，比如把高频报错写进 Skill。这样循环越转越稳，这才是普通开发者能掌控的、属于自己的 Harness。
