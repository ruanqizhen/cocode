# 实战：回音堂 Anachron——用 AI 从零做一个历史人物论坛

> “前事不忘，后事之师。”——《战国策》

前面几章讲的都是方法：怎么写提示词、怎么管上下文、怎么写项目宪法、怎么让多个 Agent 分工、怎么控制成本。方法讲多了，容易给人一种错觉：只要方法对，项目就会自己长出来。

这一章反过来：讲一个真实的项目，看这些方法落到一个具体产品上时，到底长什么样，哪里顺手，哪里卡壳。

这个项目叫 Anachron，中文名是回音堂，线上地址是 anachron.qizhen.xyz，代码开源在 ruanqizhen/anachron。它是一个历史人物论坛：用户可以发帖、回帖，也可以“召唤”历史人物，让 AI 扮演的人物下场参与讨论。曹操可以和祢衡吵架，王安石可以跟海瑞辩论变法——吵得越像本人，这个论坛就越成立。

本章不讲“AI 多么神奇”，只讲四件事：产品怎么定、技术栈为什么是这个组合、人物是怎么“演”出来的、成本和治理怎么兜底。读完你应该能直接抄走它的结构，去做自己的下一个项目。

## 先说清楚：这是一个什么产品

回音堂最开始的一句话其实很简单：

> 做一个论坛，让用户扮演历史人物，让 AI 扮演的历史人物互相辩论。

一句话里有两个坑，新手最容易同时掉进去。

第一个坑是“论坛”两个字。论坛听起来简单，做起来全是细节：板块、帖子、回帖、楼中楼、点赞、通知、举报、审核、登录、游客发帖……每一项单独看都不难，加起来就是一个中等复杂度的 Web 应用。AI 最擅长的恰恰是“每一项单独看都不难”，最不擅长的是“加起来还不乱”。

第二个坑是“历史人物”四个字。人物一多，人设就容易串味。今天曹操还在谈唯才是举，明天就开始用网络用语讲管理学；祢衡骂人骂到一半，突然变得彬彬有礼。这不是模型“变笨了”，而是约束没给够。后面会讲，约束不是写在聊天框里的一句话，而是写进数据表和代码里的结构。

所以立项的第一步，不是马上写代码，而是把产品砍到“一条线能跑通”：

1. 用户能发帖、回帖；
2. 能选一个历史人物；
3. AI 人物能针对这条帖子回一帖；
4. 回帖要一眼看得出是 AI 发的。

就这四条。板块、通知、搜索、后台管理、每日 digest，都是这条线跑通之后再加的。AI 编程最常见的失败，不是一开始写不出来，而是第一版就想把所有功能一次写全，结果上下文爆炸，谁也改不动。

## 技术栈：为什么是 Vite + React + Supabase，而不是别的

回音堂真实的技术栈是这样的：

- 前端：Vite + React 19 + TypeScript + Tailwind CSS 4，用 React Router 做路由；
- 后端：Supabase（Postgres 数据库 + 身份认证 + Edge Function）；
- 部署：Cloudflare Pages，另有一层 `functions/_middleware.js` 做服务端渲染注入，主要是给搜索引擎和分享卡片补内容；
- 代码结构：`src/pages/` 放页面（Home、Board、Thread、Characters、Login、Search 等），`src/components/` 按 forum、layout、admin、ui 分组，`src/lib/` 放 API、类型、认证等公共逻辑，`supabase/functions/` 放服务端函数。

这个组合对 AI 协作友好，有三个很实际的理由，不是玄学：

第一，前后端分工干净。前端只管展示和交互，所有“需要密钥、需要鉴权、需要调大模型”的事，都放在 Supabase Edge Function 里。这样 AI 在改前端时，不会顺手把密钥写进浏览器代码；改后端时，也不用在十几个页面里找调用点。

第二，数据结构就是产品结构。人物、板块、帖子、回帖、AI 回复任务，全部是数据库里的表，改产品就是改表和改读表的地方。AI 最怕的是“逻辑藏在各处”，最喜欢的是“事实只存在一个地方”。

第三，部署链路短。前端是静态站点，改完就能发；服务端函数独立部署，改人物回复逻辑不用动前端。链路越短，AI 出错后你定位问题就越快——是构建错了、路由错了，还是数据库权限错了，一眼就能分出来。

这里要提醒一句：选型没有标准答案。Next.js、SQLite、Prisma 都是好工具，但它们不是回音堂实际用的组合。写书、写复盘时，最忌讳的就是把“听说过的流行组合”写成“自己项目用的组合”。读者照着抄，跑不起来，信任就没了。技术选型那一节，宁可写得少一点，也要写自己真正验证过的。

## 项目宪法：写在仓库里，而不是写在聊天里

项目一到几千行，AI 就会开始“好心办坏事”：为了加一个功能，在三个地方各写一遍相似函数；改一个类型定义，顺手把别处也改崩；为了图省事，把本该走服务端的调用直接写进前端。

前文《项目宪法》一章讲过对策：把规则写进仓库，让每一轮对话都自动加载。对回音堂来说，一份能直接用的宪法不用长，二十行左右就够了，关键是每一条都要“可验证”：

```markdown
# Anachron 项目宪法（节选）

## 命令
npm run build
npm run lint

## 结构
src/pages/：页面；src/components/：组件；src/lib/：公共逻辑与类型
supabase/functions/：服务端函数；数据库改动只走 migration，不直接改线上表

## 红线
- 前端永远不直接用 service_role key，所有调模型、写 AI 回帖的操作只走 Edge Function
- 新增字段先改 src/lib/types.ts，再改调用处；不许用 any 蒙混过关
- AI 发的帖子必须带 is_ai_post = true，前端必须标明身份
- 改已有文件前，先读它的调用方；改数据库前，先读 migration
```

注意最后一条的措辞：不是“写好代码”，而是“先改 types.ts，再改调用处”。AI 听得懂、检查得出来的规则，才是规则；听起来很对、没法检查的，都是口号。

宪法还有一个作用，是帮你“拒绝”。AI 提议加一个很酷的功能时，你可以对照宪法问一句：它破坏哪条红线？要不要为它专门改表、改权限？很多技术债，就是在“这次先将就一下”里欠下的。

## 人物不是提示词，是一张数据表加一段组装逻辑

这是本章最核心的一节，也是回音堂和一般“角色扮演聊天室”最大的区别。

新手做人物，第一反应是写提示词：“你现在扮演曹操，要霸气一点。”这样写，前三轮很像，第十轮就串了。因为“霸气”不是可执行的数据，模型只能凭感觉发挥。

回音堂的做法是：人物先是一条数据库记录，再由代码拼成提示词。

```typescript
export interface AICharacter {
  id: string;
  era: string;              // 如“东汉末年”
  tags: string[];           // 如 ["法家", "军事", "诗歌", "霸道", "实用主义"]
  birth_year: number | null;
  death_year: number | null;
  is_active: boolean;       // 总开关：出问题先关掉这个人物，不用改代码
}

export interface Profile {
  id: string;
  username: string;
  bio: string;              // 人物小传，是人设的第一手材料
  is_ai_character: boolean;
}
```

种子数据里就有现成的对比组：曹操和祢衡。一个是“唯才是举、不拘一格”的实用主义者，一个是“恃才傲物、语不惊人死不休”的狂士。把这两个人放在同一个帖子里，辩论自然就有张力——张力来自数据本身的反差，而不是提示词里写“请激烈辩论”。

真正发给模型的系统提示词，是由上面这些字段组装出来的，大意是：

```text
你正在扮演曹操（155—220），东汉末年。

行为准则：
- 始终以第一人称、以你的真实历史性格发言，不要试图理解现代观点
- 观点和语言都要符合你的时代和身份背景
- 要用历史上的真实案例论证，不要只表达态度和情绪
- 直接输出回复内容，不要加旁白、动作描写和括号
- 用白话文回答，可以带一点当时的语言习惯，但要让现代人读得懂
- 回复长度在 100～400 字之间
- 禁止使用现代网络用语或表情符号
- 回复末尾无需署名
```

这段提示词有几个值得抄的细节：

第一，给了“认知边界”：不要试图理解现代观点。一个东汉末年的人，本来就不该懂互联网、懂现代管理学。边界给清楚，穿越和幻觉就少一半。

第二，给了“论证方式”：用真实案例，不要只表态。AI 最容易滑向的，就是态度正确、内容空洞的“正确的废话”。要求举案例，等于逼它把知识拿出来，而不是把情绪拿出来。

第三，给了“格式硬约束”：字数、不要旁白、不要括号、不要网络用语。这些不是审美，是可检查的。回复超长、带了“（捻须微笑）”，一眼就能发现，测试也好写。

第四，人物可以一键关闭。`is_active` 这个字段平时不起眼，出问题时就是救命开关：某个人物被玩坏了、被用户诱导说错话了，先关掉它，再慢慢修提示词，不要让它一边惹祸一边等你修。

## AI 回帖为什么要走队列，而不是直接调模型

用户发帖后，AI 人物不是在浏览器里直接调大模型接口，而是走了一条队列链路：

```text
用户发帖
  → post-handler（接住发帖事件）
  → dispatcher（决定召唤哪个人物）
  → ai_response_queue（写入一条待处理任务）
  → character-responder（Edge Function，真正调模型）
  → 写回 posts 表，标记 is_ai_post = true
```

任务表里有状态：`pending`（待处理）、`processing`（处理中）、`done`（已完成）、`failed`（失败），还有 `retry_count`（重试次数）和 `error_message`（错误信息）。失败了先重试，最多重试一次左右，隔一段时间再试，实在不行就标记失败，不让它无限循环烧钱。

为什么要绕这么大一圈？三个原因，都是血泪换来的：

第一，调模型会失败、会超时、会排队。直接在用户请求里调模型，用户就要对着转圈等；一旦失败，帖子发没发、AI 回没回，全乱了。队列把“用户发帖”和“AI 回帖”解耦：前者立刻成功，后者慢慢完成，失败了也有记录可查。

第二，上下文要可控。`character-responder` 每次只取三样东西：帖子标题和所属板块、最近最多 10 条已发布回帖、触发 AI 回复的那一条帖子。不是整个论坛历史，不是全量向量检索。10 条这个上限，就是上下文工程在真实项目里的样子：不是“越多越好”，而是“够用、稳定、可预测”。

第三，供应商要能切换。主供应商出问题时，自动切到备用供应商；备用也没有，再看有没有配第三个。切换逻辑写在服务端函数里，前端完全不知道。这比“在每个调用点都写一遍 try/catch”可靠得多，也比“等主供应商恢复”体面得多。

顺带说一句：本章没有给你一个“向量数据库 + RAG，成本降 80%、延迟降 60%”的故事。不是 RAG 不好，而是回音堂现阶段并不需要它——10 条上下文已经够一场辩论用了。优化要先有账本：每次调用记下供应商、模型、输入输出 token 数、耗时、成功失败，跑一段时间再谈百分比。没有账本的百分比，都是写给自己看的安慰剂。

## 阿谀奉承和幻觉：靠什么防，而不是靠一个“裁判 AI”

很多人一遇到“AI 互相吹捧、胡编历史”，第一反应是再加一个 AI 当裁判，让它给辩论双方打分、发黄牌。这个思路听起来很 AI，实际效果往往一般：裁判自己也会幻觉，而且多一次调用就多一次成本和延迟。

回音堂更实际的做法，是把防线拆成四层，每层都不依赖“再加一个更聪明的模型”：

第一层，数据约束。人物有时代、生卒年、标签，提示词里有认知边界。让曹操去评价宋代的事，本身就是数据上不该发生的事——要么是召唤逻辑选错了人物，要么是帖子板块分错了时代，先修这两个地方，比事后纠错便宜。

第二层，提示词约束。第一人称、真实案例、字数上限、禁用现代用语，这些都是在“生成之前”就把跑偏的空间压小。约束越具体，模型自由发挥的余地就越小。

第三层，对抗测试。别只测“曹操谈唯才是举”这种顺境，要专门测逆境：让祢衡当面骂曹操，看曹操会不会突然变得温顺、开始赞美对方；让人物评价自己死后几百年的事，看它会不会一本正经地“穿越”。把这些用例记下来，每次改提示词都重跑一遍。这就是前文《测试》一章讲的回归测试，只不过测的是人设，不是函数。

第四层，人来兜底。帖子有 `published`（已发布）、`pending_review`（待审核）、`rejected`（已拒绝）三种状态；用户可以举报，管理员可以在后台处理；AI 的帖子必须标明身份。这不是“不信任 AI”，而是论坛的基本诚信：读者有权知道，这段话是历史人物“演”出来的，还是真人说的。治理规则写进产品里，比写进提示词里管用。

## 成本控制：先记账，再谈优化

AI 论坛最烧钱的地方，从来不是某一次调用特别贵，而是调用次数悄悄涨上去：每个帖子都召唤三个人物，每个人物都带上全部历史，失败了无限重试——月底账单一看，才发现问题。

回音堂现成的节流阀，其实都已经在前面出现过了，只是换个角度再看一遍：

- 回复限长：100～400 字。字数上限就是成本上限。
- 上下文限量：最近 10 条已发布帖子，不是全量历史。
- 队列限流：任务有状态、有重试上限，失败不会无限循环。
- 供应商切换：主备切换是为了可用性，顺带也避免了“某个供应商涨价或限流时只能硬扛”。
- 后台任务分开算：每日 digest 这类汇总任务走独立的函数，不占用实时回帖的预算和延迟。

如果你要接手优化，正确的顺序是：先把每次调用的账记下来，再挑最大头开刀。是上下文太长，就砍上下文；是重试太多，就修触发逻辑；是某个供应商特别贵，就调切换顺序。反过来，先上向量数据库、先换更贵的模型、先加裁判 AI，都是在没有账本的情况下花钱。

## 人类最后做的三件事

回到这本书开头的问题：AI 这么能干，人还剩下什么？

在回音堂这个项目里，答案很具体，不是“导演”这种漂亮的比喻，而是三件没法外包的事：

第一，定边界。做什么、不做什么。时代分区怎么做（夏商周、秦汉三国、隋唐、明清……），哪些人物可以上、哪些先不上，游客能不能发帖、发帖要不要审核——这些决定没有正确答案，但必须有人拍板。AI 可以给你十个方案，选哪一个，是你的事。

第二，定标准。项目宪法怎么写、人物回复多长算合格、AI 身份怎么标明、什么情况下关掉一个人物。标准一旦定下来，AI 才能沿着它走；标准含糊，AI 只能凭感觉走。

第三，兜底。审核、举报、管理员后台、人物总开关、队列里的失败任务——这些东西平时没人夸，出事时全靠它们。AI 可以帮你写这些功能，但“出事时由谁负责、按什么流程处理”，只能是人来定。

AI 写了大部分代码，设计了不少提示词，甚至帮你把站部署上线。但“这个论坛到底想讲什么样的历史、想让什么样的人在这里说话”，是人先想清楚的。代码可以外包，品味和责任外包不出去。

## 试一试

读完这一章，别只点头，动手做三件小事：

1. 加一个人物。照着种子数据的格式，写一条新人物：小传、时代、生卒年、标签，再想一句“这个人物绝不会说的话”。然后让他和一个性格相反的人物辩论一次，看他有没有说出那句绝不会说的话。
2. 给自己的项目写一份二十行的宪法。只写可验证的：命令是什么、目录怎么分、密钥放哪里、什么事不许做。写完发给 AI，让它按这份宪法改一次代码，看它有没有违反。
3. 打印一次真实的上下文。把某次 AI 回复时真正发给模型的标题、板块、10 条帖子、触发帖列出来，数一数大概多少字，再试着砍掉一半，看回复质量变差了没有。砍完还够用，说明你以前一直在为用不上的上下文付钱。
